# 🌳 Komorebi 3D — 開発・チャット運用ルール

> **用途:** 新しい「00｜統合開発」チャットのチャッピーが守る、比較的長期の作業ルール。
> **正本:** GitHub `shuma-fujita1012/komorebi` の `main`。
> **更新方針:** このファイルは `docs/STATUS.md` の定期更新では書き換えない。ルールの変更はユーザーと相談し、明示的な了承を得てから小さくコミットする。

## 1. 新しいチャットで最初に読むもの

1. **`docs/WORKFLOW.md`**（このファイル）で運用ルール・モック生成手順を確認する。
2. **`docs/STATUS.md`** で現状・未完了タスク・PASS範囲・変更禁止資材を確認する。
3. 必要な**現行ソースをGitHub `main` から読む**。コードの現状は古い引き継ぎ文より最新ソースを優先する。
4. 以前に合格した工程を勝手にやり直さず、ユーザーが現在指定している作業から進める。

`STATUS.md` は「いまどこか」、本ファイルは「どう進めるか」。両者の内容を混同しない。

## 2. GitHub・検証・資材保護

1. **GitHub `main` がコードの正本。** 通常バックアップ用ブランチを増やさず、変更は小工程でコミットする。コードの閲覧・検証はよいが、**GitHubへの作成・更新・削除・コミットはユーザーの明示的な許可を得てから**行う。
2. **開発入口は `komorebi3d/dev.html`。** 固定Engine参照、Git履歴、安定版v0.7/v0.6などの保護資材を無断変更しない。詳細な対象は `STATUS.md` で確認する。
3. 通常のゲームHTMLは `dev.html` ＋ 最新実機PASS版 ＋ 前世代実機PASS版の3本。`mock.html` は別目的の**軽量UI検証ページ**であり、製品の安定版やアーカイブではない。不要な保存用HTMLを増やさない。
4. **検証結果を区別する。** 静的・構文・模擬・ビルド検証と、GitHub Pages公開版でのユーザー操作、iPhone/iPad Safari実機確認を混同しない。報告されていない端末別PASSや全配置の網羅PASSを推測しない。
5. GitHubのコミットとGitHub Pages配信・Safariキャッシュ反映は別。画面のコミット表示だけで配信HTMLのSHAを証明したことにしない。
6. 開発作業と引き継ぎは原則「00｜統合開発」で一元管理。実機PASS後・方針変更後・チャット移行前に `STATUS.md` の**状況部分**を更新する。

## 3. 質問・回答フォーム（00｜統合開発）

- 基本形：**`Q〇〇. 質問内容` → 各設問のラジオボタン → その設問の任意コメント欄**。
- 複数の確認事項は**1つのフォーム**にまとめ、送信ボタンは最後に**1個**。送信時は全設問の選択結果・コメントを**Q番号付きで1回のチャット送信**にまとめる。
- 単独質問でも同じ基本形を使う。コメントが空でも送信でき、不要な質問は増やさない。チャット内で操作できるラジオ等を優先する。
- 同じチャット内のQ番号は順番に進める。新しい「00｜統合開発」チャットを作り直した場合はQ1から開始してよい。

## 4. 「チャットに2パネルのモックを出して」と頼まれた場合

### 4.1 モック専用ソースを出発点にする

- **必ずGitHub `main` の軽量モック専用ソースを確認する。** 本番 `dev.html`・`dev.template.html`・`panels/game.html`・`panels/game.css` からゲーム部分をコピーして組み立て直さない。
- **2パネルの参照元**：
  - `komorebi3d/mock.template.html`（モックの外枠・配置・起動）
  - `komorebi3d/mock-layout.css`（モック専用レイアウト）
  - `komorebi3d/panels/game.mock.html`・`game.mock.css`（黒いゲーム仮画面＋ⓘ）
  - `komorebi3d/panels/build.html`・`build.css`（開発情報パネル）
  - `komorebi3d/common.css`（必要な共通スタイル）
  - `komorebi3d/dev-panel-layout.js`（共有のパネル操作ロジック）
- パネルの構成・呼び出し・スタイル・操作の**最新仕様はソースを読んで確認**し、古いチャットの記憶だけで再実装しない。
- **本番Game Engine、WebGL/Canvas描画、ゲーム入力、テスト操作パネル、実行ステータスパネル、その関連JSは2パネルモックに含めない。** ゲーム表示は黒い仮画面とⓘで十分。

### 4.2 チャット内での再現手順

1. 上記の専用ソースから、チャット内で動く**軽量な操作可能モック**を構成する。外部モジュールをチャット内へそのまま読み込めない環境では、必要部分だけを同等の挙動で再構成し、本番コードに差し替えない。
2. ⓘ押下中の説明＋ゴミ箱表示、ドラッグ交換・削除、空き枠の＋から再追加、**スロットの高さ固定**、iPhone相当の縦並び／iPad相当の2列レスポンシブを維持する。既存の共有操作仕様から不要な独自操作を足さない。
3. **大きなモックを表示する前に、生成予定コードの行数・文字数を実測して先に別の返答で報告し、ユーザーのOKを待つ。** コード量を推測で提示しない。承諾を得た次の返答でモックを表示する。
4. モック表示を依頼されただけでは、GitHub上のファイルを変更・コミットしない。チャット内プレビューのPASSと公開URLの実機PASSは別々に記録する。
5. 不足している機能を勝手に本番Engineから持ち込まない。要件が変わったら先に範囲を確認し、変更部分のコード量を把握する。

### 4.3 ビルド／公開URLとは別の概念

- **ビルド切替**：`node komorebi3d/build-dev.mjs --mode=mock` は `komorebi3d/mock.html` を生成する。
- **本番生成**：`node komorebi3d/build-dev.mjs --mode=product`、または引数なしは `komorebi3d/dev.html` を生成する。
- **チャット内のモック表示**は、このGitHubのモック用ソースを手本にした別のプレビュー。ビルドコマンド実行やGitHubコミットを必須にしない。
- 生成ファイルとソースの一致を確認する場合は、対象モードの `--check` を使う。2パネルから3/4パネルへの拡張は、ユーザーから指示があるまで勝手に進めない。

## 5. 本ファイルの保守

- 新しい運用ルールはここに追記・修正し、`STATUS.md` には必要な参照と**現在の作業状態だけ**を記録する。
- `STATUS.md` の頻繁な更新に、本ファイルの変更を紛れ込ませない。
- 仕様変更があった場合、実コードが正本。ここにあるファイル名や手順も必要に応じてユーザーの了承のもとで更新する。
