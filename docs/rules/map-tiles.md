# 🌳 Komorebi 3D｜OSMタイル分割専用ルール

> **適用先：将来のタイル分割Pythonおよび分割用GitHub Actionsのみ。**
> 取得用ワークフローや取得スクリプトに、この分割仕様を依存させない。
> 現在は**仕様記録のみ**であり、この文書自体は分割処理を実装・実行しない。

## 1. 唯一の責務

入力済みOSM JSONの各要素を、松戸駅基準の固定 **2,000m × 2,000m** グリッドへ振り分け、タイル別JSONに保存することだけを担当する。

**基本原則：元のOSM情報を可能な限り無加工で保存する。** 地物の形状がタイルをまたぐ場合の複製のみ例外とする。分割のための座標投影・交差判定は行うが、元の緯度経度を投影値で置き換えない。

- 入力JSONは読み取り専用とし、上書きしない。
- `type`、`id`、`version`、`tags`、`lat`/`lon`、`geometry`、`members`、その他入力にあるフィールドを削除・加工しない。
- 元入力の各OSM要素を、そのまま対象タイルの `elements` に格納する。タイル単位のメタデータのみ最小限追加してよい。
- 単一タイル内に同じ入力要素を判定経路の違いで二重登録しない。
- 読み込む入力データの取得方法、取得半径、日時に依存する特別処理を設けない。

## 2. 変えてはいけない固定グリッド

| 項目 | 固定値・規約 |
| --- | --- |
| 基準位置（WGS84緯度・経度） | `35.78444, 139.90061`（この数値を丸め直さない） |
| 投影座標系 | `EPSG:6677`（JGD2011 / Japan Plane Rectangular CS IX） |
| タイル寸法 | 東西2,000m × 南北2,000m |
| 基準タイル | 上記基準位置の投影座標を**中心**に持つ `tile_0_0` |
| Xインデックス | 東を正、西を負 |
| Yインデックス | 北を正、南を負 |
| 識別子 | `tile_x_y`（例：`tile_1_-1`） |

計算規約：
1. 基準緯度経度と地物の緯度経度を、同じ固定変換条件でEPSG:6677へ投影する。ライブラリの軸順の違いに注意し、入力経緯度は **(経度, 緯度)**、計算上の平面座標は **(東向きX, 北向きY)** に統一する。
2. 原点 `(E0, N0)` は上記基準位置の投影値。タイル `(x,y)` の範囲は、東向き `[E0 + 2000x - 1000, E0 + 2000x + 1000)`、北向き `[N0 + 2000y - 1000, N0 + 2000y + 1000)` と定義する。
3. 点が境界にある場合は下端・左端を含み、上端・右端を含まない半開区間で一意に所属させる。
4. **線・面がタイル境界と接する場合は、交差する双方のタイルに完全な地物を複製してよい。** この境界ルールを実装時にテストする。
5. 25km→30kmへの取得範囲変更、OSM再取得、日時変更によって、原点・タイルサイズ・境界・IDを再計算し直さない。

## 3. 地物の振り分け

- 地物の**全形状**とタイル領域の交差で所属を判定する。代表点・重心・頂点の存在だけでは判定しない。
- 複数タイルに交差するwayなどは、切断せず、元の同一OSM要素をそれぞれに完全複製する（A方式）。
- 線分がタイルを横切る場合や、多角形がタイル全体を覆う場合も、交差を見落とさない。
- relation等に直接形状がなく、入力に含まれる参照先だけでは位置を確定できない場合は、架空の形状・位置を作らない。利用可能な参照情報に基づく判定の限界は検証結果で報告する。**全relationを正しく配置できると未検証のまま断定しない。**
- 地物を分割して別OSM IDにしたり、簡略化したり、タグを修正したりしない。
- 分割された別タイルに同じOSM IDの要素が現れることは正常。ゲーム側の重複描画対策は分割処理に含めない。

## 4. 出力と日時

- タイルファイル名は `tile_x_y_YYYYMMDDHHMMSS.json`。
- 14桁は**JSON生成日時（UTC）**。OSM本体の更新日時とは区別する。画面に表示する際のJST変換はゲーム側の責務。
- タイルIDは日時を含まない `tile_x_y` とし、名前の日時を変えても同じIDは同じ地理範囲を指す。
- 各タイルの現行ファイルは原則1世代のみを管理する。旧版の保存・切替・キャッシュの仕様をこの分割規則に持ち込まない。
- 出力JSONには入力の `elements` とOSMの属性を保持し、タイルID・生成日時等の必要最小限のメタデータのみ追加する。インデックス形式・配信方式の詳細は別途決定可能。
- 巨大入力はメモリ負荷やGitHubの単一ファイルサイズ制限に注意し、分割後に各出力ファイルのJSON妥当性・要素保持・サイズ・境界交差を検証する。

## 5. 取得円の外周

- 入力データにある地物だけを割り当てる。元の25km取得円にかかるタイルも、そのまま出力する。
- 円外の不足データをAPIへ取りに行かない。欠損を推測・補完しない。
- **部分収録フラグは不要**。空白エリアの描画可否はゲーム側で判断する。

## 6. 分割工程では絶対に行わないこと

- OSMデータのAPI取得・再取得・追加ダウンロード
- OSMの鮮度判定、新旧比較、自動更新、タイル間不整合の修復
- 形状の切断・簡略化・補完、座標の書換え、OSMタグの編集
- 3Dメッシュ変換、描画用最適化、プレイヤー位置・表示範囲の判断
- ゲーム側のキャッシュ制御、非同期通信、警告表示、ボタン操作

## 7. 将来の変更時

**固定グリッド互換性・元OSM要素の無加工保持・跨ぎ地物の複製・責務の分離**を最優先する。同じ入力と同じグリッド条件では同じ地物割当を再現する（生成日時だけは実行ごとに変わり得る）。

分割用GitHub Actionsを新設する際は、**そのYAML冒頭から本ファイルを参照**し、分割実行スクリプトにも本規則への参照を置く。取得用Actionにはこの全文を複製しない。
