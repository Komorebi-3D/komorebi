# 🌳 チャット内モックの生成・表示ルール

## チャットごとの役割と承認フロー

- **「00｜統合開発」：開発・修正・試作。** モックの作成や変更に伴い大きなコードをチャットへ表示する前に、出力予定コードの行数・文字数を実測して別の返答で報告し、ユーザーの明示的な承認を待つ。
- **「01｜モック」：完成版の表示・保管専用。** GitHub `main` の `komorebi3d/mock.chat.html` を取得して、そのままインタラクティブなAppBlockとして表示する。**文字数・行数の事前報告、表示の承認確認、確認質問は不要。** 初回表示とユーザーから明示的に依頼された再取得の両方に適用する。
- 「01｜モック」での表示のみを理由に、GitHubのファイル変更・ビルド・コミットを行わない。GitHub取得に失敗した場合は代替モックを作らず、理由を簡潔に説明する。
- 上記の区分は**表示前承認の要否**に関するものであり、HTML・CSS・JavaScriptの原文維持や操作機能の保持といった要件は変えない。

## 1. パネル数・種類・配置を独立して扱う

チャット内モックは、依頼に応じて**1～4パネル**を表示する。パネルの**数・種類・配置位置**はそれぞれ独立した条件であり、「2パネルなら上＋左」のような固定の組み合わせを前提にしない。

| 指定事項 | 選択肢 |
| --- | --- |
| パネル数 | 1、2、3、4 |
| パネルの種類 | `build`＝🧪開発情報、`game`＝🎮ゲーム画面、`test`＝🧪テスト操作、`runtime`＝📊実行ステータス |
| 配置スロット | `top`＝↑上、`left`＝←左、`right`＝→右、`bottom`＝↓下 |

- **ユーザーが指定したパネルとスロットだけを初期配置**する。不要なパネルを人数合わせで追加しない。同じパネル種類を複製したり、2種類を同一スロットに重ねたりしない。
- 数・種類・位置の一部が省略されている場合は、**直近で確定した構成を引き継ぐ**。新しいチャットなどで、その履歴が確認できず構成を特定できなければ、必要な不足条件を確認する。勝手に標準配置を決めない。
- 1パネルの場合も要求されたスロットへ配置する。空きスロットの表示・追加メニューは、**モックに実際に存在するパネル・スロット**の範囲で扱う。
- 「1～4パネルで表示できるようにする」という**チャット内モックの作成方針**と、実際に作成・検証済みのモックやビルド機能の対応範囲を混同しない。

## 2. GitHub `main` の軽量モックソースを出発点にする

- **まずGitHub `main` の最新のモック専用ソースを読む。** 本番 `dev.html`、`dev.template.html`、`panels/game.html`、`panels/game.css` のゲーム本体を複製して、チャット内モックを作り直さない。
- 現在あるモック用ソースは次のとおり。**これらは現在の2パネル構成向け**なので、1・3・4パネルへの自動対応を意味しない。
  - `komorebi3d/mock.template.html`：2パネル用の外枠・配置・起動
  - `komorebi3d/mock-layout.css`：モック専用のレスポンシブ配置
  - `komorebi3d/panels/game.mock.html`・`game.mock.css`：黒いゲーム仮画面とⓘ
  - `komorebi3d/panels/build.html`・`build.css`：開発情報パネル
  - `komorebi3d/common.css`：共通スタイル
  - `komorebi3d/dev-panel-layout.js`：共通のパネル操作ロジック
- `test` や `runtime` が要求された場合は、最新ソースと要件を確認し、**軽量なモック用部品がなければ必要最低限を用意**する。本番ゲームのEngine、WebGL描画、ゲーム入力、未指定のパネル専用処理を無断で含めない。操作の模擬が必要なら、本物のGame APIと区別できるモックを用いる。
- **既存のモック用HTML・CSSと共有JSを原則として原文のまま利用する。** 文字数の削減はまず正本の軽量化・ビルド時の選択で行い、チャット用に同じ機能を新しく書き直して別実装を作らない。不要な本番コードを取り込まず、既存の共有仕様を勝手に改変しない。

## 3. チャット内表示の進め方

### 3.1 確定版はチャット用完成ファイルを無加工で利用する

1. パネル数・種類・位置と今回の確認目的を、ユーザーの指定と直近の確定内容から特定する。
2. **チャット表示時は、まずGitHub `main` の確定版 `komorebi3d/mock.chat.html`（チャット用の自己完結型生成物）を確認する。** 対応する構成のファイルが生成・検証済みなら、その中身を**1文字も書き換えず**チャット表示用の枠に渡す。新しいチャッピーによるimport解消・JS結合・HTML加工・別実装は不要にする。
3. **`mock.chat.html` は手編集しない生成物。** HTML・CSS・共通操作JSは本番と共有する元ソースを正本として、確定時に生成する。生成済みファイルにJSが内蔵されていても、本番とモックの操作処理を二重メンテナンスしない。
4. 対応する完成ファイルがまだない場合は、`komorebi3d/mock.html`・`komorebi3d/dev-panel-layout.js`・`mock.template.html`・関連CSSを確認し、**「未生成／未検証」と明示**する。新しいチャットで毎回加工する運用を標準とせず、生成方式の実装・テストを優先する。代替表示が必要なら、変換が発生することを説明しユーザーと相談する。
5. チャット内で要件検討用のモックを変更する場合は、**確定版から派生した一時的な試作**として扱い、パネル操作や共通仕様を独自に書き直して恒久的な別ソースにしない。新たな構成（1・3・4パネルなど）が未対応の場合も、実装済み範囲と試作箇所を区別する。
6. **「GitHub原文をそのまま表示した」のか「チャット内で試作・変更した」のかを明示**する。新しいチャットでも再現できることを目標に、正本との不明な差分を残さない。

### 3.2 表示・検証・変更の扱い

1. 共有仕様であるⓘ押下中の説明とゴミ箱、ドラッグ交換・削除、空き枠の＋からの再追加、**スロットの高さ保持**、レスポンシブを維持する。既存の仕様にない操作を独自に追加しない。
2. **「00｜統合開発」でモックの新規作成・修正・試作を行う場合**は、実際に出力する予定のコードの行数・文字数を実測し、別の返答で報告する。**ユーザーのOKを待ってから表示する。** GitHubソースの行数・文字数を、そのまま表示コードの実測値として流用しない。
   - **「01｜モック」でGitHub `main` の完成済み `komorebi3d/mock.chat.html` を再取得して無加工表示するだけの場合は、コード量の報告・承認待ちを不要とする。** GitHubから取得できたら、同じ返信で直接AppBlockに全文を表示する。ファイルサイズの増減も再承認の理由にしない。
   - 「01｜モック」であっても、完成ファイルの改変・新規設計・試作を依頼された場合は、表示専用の例外を適用せず「00｜統合開発」で相談する。
3. モック表示の依頼だけではGitHubを変更・コミットしない。チャット内モックのPASS、ビルド生成のPASS、公開版・Safari実機PASSを分けて記録する。

## 4. ビルド引数とチャット内モックを区別する

- `node komorebi3d/build-dev.mjs --mode=chat` は、既存の2パネルモックのHTML・CSSと共通 `dev-panel-layout.js` から、**チャットへ無加工で貼るための自己完結HTML断片 `komorebi3d/mock.chat.html`** を生成する。元コードにJSの別実装を増やさない。
- 現在の `node komorebi3d/build-dev.mjs --mode=mock` は、**既存の2パネル（上＝build、左＝game）**を `komorebi3d/mock.html` に生成する。引数だけで任意の1～4パネル構成を生成する機能ではない。
- `node komorebi3d/build-dev.mjs --mode=product` と引数なしは、既存の4パネル本番開発ページ `komorebi3d/dev.html` を生成する。
- `--check` はソースと生成HTMLの一致検証。`--mode=chat --check` も対応。チャット内モックを表示するだけなら、ビルドコマンドやGitHubコミットは不要。
- ビルド側を別のパネル数・配置に対応させる変更は、**ユーザーが指示した場合に別工程として設計・検証**する。チャットの「モック出して」をその変更の許可と解釈しない。

## 5. チャット用完成モックの生成・開発サイクル

**モックの主目的は、チャット内で要件をすばやく視覚的に伝え、試行錯誤すること。** Safari用公開ページの整備やGitHubコミット自体を目的にしない。モックの仕様検討は本番実装より先に進んでよい。

1. **確定済みの出発点を表示：** 前回の確定時に生成・コミットした `komorebi3d/mock.chat.html` を、次のチャットで**内容を1文字も加工せず表示**する。表示用の枠への貼り付けはよいが、ファイル本文を手作業で変換しない。
2. **要件検討中：** チャットに出したモックをその場で自由に変更して相談・確認する。**変更のたびにビルドしたり、GitHubへコミットしたりしない。** この段階で本番とモックに差があるのは意図した状態であり、GitHubの確定版も勝手に更新しない。
3. **要件確定後：** チャットで合意した仕様を本番の共有ソース・必要な専用部品へ反映し、必要なコード検証とユーザーの確認を行う。ⓘ・ドラッグ・削除・再追加・高さ固定などの共通処理は本番とモックで**同一ソースを使い、二重メンテにしない**。
4. **本番修正・検証が完了したコミット直前：** 既存の `komorebi3d/build-dev.mjs` の **`--mode=chat`** で、最新の共有ソースから `komorebi3d/mock.chat.html` を自動再生成する。外部JSのimport解消・JSの埋め込み・必要なチャット環境への適合は**この生成工程で完結**させる。チャットに表示するたびに変換しない。
5. **生成結果を確認して同じ工程でコミット：** 本番とモックの整合性・コード量・チャットでの無加工表示と操作を検証し、合格した確定版を本番修正と一緒にコミットする。次回以降はその完成ファイルを新しい出発点にする。ユーザーの明示的な許可なしにGitHubへ書き込まない。

### 完成ファイルの合格条件

- **新しいチャットで、新しいチャッピーが完成済みのモックコードを1ファイルからコピーし、1文字も書き換えずにチャット内へ表示でき、操作も正常に動くこと。**
- チャット表示時に追加のimport解消・結合・独自JS再実装を必要とせず、Engine本体など不要な依存も含まないこと。
- 本番と共通の機能は同じ元ソースから生成され、**本番／軽量モック／チャット用確定版の三重メンテを生まない**こと。
- HTML/CSS/JSの構造確認だけでPASSとせず、チャットでの表示とⓘ・ドラッグ交換・削除・再追加・高さ固定・レスポンシブの必要な実操作を確認すること。

**実装状態（2026-11-10）：** `--mode=chat` で `komorebi3d/mock.chat.html` を生成可能。HTML・CSS・共有操作JSを単一HTML断片へ組み込み、相対importを解消する。`--mode=chat --check` で生成物と正本の一致を確認する。**生成結果の静的整合性はPASS済み。ただし、新しいチャットでの1文字も加工しない貼り付け表示・ⓘ/交換/削除/再追加/高さ固定の実操作は未PASS。** チャット内で確認できるまで最終合格扱いにしない。
